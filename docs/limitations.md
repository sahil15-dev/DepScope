# Current limitations

- Requirements files provide declared pins. Included files, environment markers, private indexes, and non-registry sources require separate verification. A matching public package name and version can still refer to a privately supplied artifact when the manifest omits source metadata.
- npm lockfile versions 1–3 provide installation entries. DepScope preserves occurrence paths and the information available about direct and transitive dependencies. Local or bundled sources, unsupported paths, and explicit non-public resolutions are recorded as unresolved. The engine does not reconstruct all npm dependency edges or check what is currently installed.
- OSV coverage varies by package, ecosystem, and observation time. A completed empty lookup means the provider returned no matching records for that coordinate. Request failures, unsupported advisory ranges, and contradictions can leave discovery-only findings or partial coverage.
- DepScope evaluates PEP 440 ecosystem ranges for PyPI and SemVer ranges for npm. It retains other affected range data where available. It does not evaluate Git ancestry, fetch references, inspect runtime reachability, or test whether a change is compatible.
- A fix is evidence for the particular advisory-supported version interval. Missing or ambiguous fix evidence requires manual review. The DepScope index weights reported severity and is capped at 100. It is a triage aid and carries scan coverage and scoring revision.
- Offline fixtures cover a small fixed set of exact coordinates and a simulated failure. Live scans send exact names, versions, and ecosystems to OSV. The API persists normalized results locally. Treat the database and exported reports as project data.
- The service runs from the source workspace with one scanner and a bounded, volatile queue. Accepted scans survive as history entries after restart, but must be resubmitted when interrupted because uploads are not persisted. Public hosting and multi-user authentication are outside the current design. See the [threat model](threat-model.md) and [roadmap](../README.md#limitations-and-roadmap).
- Comparison is available within one provenance for two finished scans with saved coverage. Explicit alias evidence can evolve between snapshots. A finding no longer detected can reflect advisory changes, dependency changes, or incomplete coverage.
- Candidate versions use applicable advisory fix boundaries and previously saved exact-version lookups. The app does not discover releases or request live validation from the remediation screen. A candidate with insufficient evidence needs independent review.
- Live risk history shows independent observations because uploads have no persistent project identity. The score cap can hide large differences in severity counts. The Phase 4 audit examined one saved live result and ran verification offline. See the [audit scope](phase4-audit.md).
- Reports contain normalized project inventory and advisory evidence from the saved snapshot. Review report contents before sharing, and use the browser print dialog for PDF export.
- An installed wheel can scan standalone. SQLite setup and bundled manifest persistence use the Alembic files and sample manifests in the project source distribution or checkout.
- Live OSV needs direct HTTPS connectivity and a trusted certificate chain. The client ignores ambient proxy settings. A lookup failure leaves coverage incomplete and cannot pass a severity policy.
- Local browser verification uses Playwright engines and recorded viewport sizes. It does not cover native mobile browsers or assistive technology.
- Project redistribution terms are pending owner approval. [Third-party notices](third-party.md)
